# Ticket Voucher System

An ASP.NET Core Razor Pages application for manually attaching Retail and F&B voucher benefits to existing ticket barcodes, printing those tickets, and tracking redemption by outlet.

## What is included

- Combined ticket package administration with optional Retail and F&B values
- Manual issuance to one or as many as 100 existing ticket barcodes
- All-or-nothing group validation and issuance in SQL Server
- A package dropdown populated from the packages created by administrators
- Individual and group A4 ticket printing with Code 128 barcodes
- Separate controller-based POS API with public lookup and redemption, lookup, and safe single-use redemption
- Voucher register, status details, audit history, user roles, dashboard, and reports

Ticket barcodes are never imported, allocated, or generated by this system. The barcode already belongs to the physical ticket.

## Structure

```text
TicketVoucherSystemApp/       Razor Pages, Identity, issuance, barcode printing, reports, and IIS
VoucherSystemApp.API/         Separate POS API: controllers and public lookup and redemption
```

## Existing database upgrade

Back up the database first. From the repository root, run:

```powershell
sqlcmd -S "YOUR_SERVER" -d "YOUR_DATABASE" -E -b `
  -i ".\TicketVoucherSystem.Database\Scripts\Upgrade-GroupIssuance-Packages.sql"
```

Use `-U` and `-P` instead of `-E` when the approved deployment account uses SQL authentication. The upgrade preserves existing tickets and vouchers, adds an internal print-batch identifier, and updates the package and issuance procedures.

These voucher tables belong to the SQL database project. Do not create an EF Core migration for them. EF Core migrations continue to manage only ASP.NET Core Identity tables such as `AspNetUsers` and `AspNetRoles`.

## New database setup

Prerequisites: .NET 10 SDK, SQL Server 2019 or newer, and SQL Server Data Tools or `sqlcmd`.

1. Create the database and configure `DefaultConnection` with user secrets for development.
2. Apply the existing Identity migration:

   ```powershell
   dotnet tool restore
   dotnet ef database update --project TicketVoucherSystemApp
   ```

3. Publish `TicketVoucherSystem.Database` from Visual Studio. The fallback SQLCMD deployment is:

   ```powershell
   cd TicketVoucherSystem.Database\Scripts
   sqlcmd -S "YOUR_SERVER" -d "TicketVoucherSystem" -E -b -i Deploy.sql
   cd ..\..
   ```

4. Configure the administrator email securely and start the application.

Do not commit production passwords or connection strings to `appsettings.json`.

## Manual workflow

1. An administrator opens `/Admin/Packages` and creates a package, for example Retail R100 plus F&B R200.
2. An issuer opens `/Operations/Issue`, selects that package, and scans one or more existing ticket barcodes.
3. SQL Server validates the complete group. If one barcode is invalid, duplicated, or already issued, nothing is saved.
4. The print screen produces one A4 ticket page per barcode and can print the complete group in one action.
5. A MICROS or HRK integration looks up and redeems the ticket barcode through the separate API. See [POS setup and walkthrough](docs/POS-API.md).

The browser test also creates a combined package, issues it to two ticket barcodes, verifies both printed pages, and confirms the removed web redemption routes reject requests.

## IIS deployment order

1. Back up the target database and the existing IIS folder.
2. Apply the database upgrade.
3. Build and test the solution.
4. Publish the web project to a temporary folder.
5. Stop the IIS application pool, replace the deployed files, and restart the pool.
6. Create a low-value test package, issue two test tickets, print both, and redeem one before reopening operator access.

## POS voucher redemption API

The separate `VoucherSystemApp.API` exposes public lookup and redemption with no authentication or authorization. See [the setup guide](docs/POS-API.md) for Swagger, Postman, database upgrade and requests.

## Webtickets barcode lookup

Administrators can open `/Admin/WebTickets`, look up a purchased Webtickets barcode, review the matching authorized ticket, and attach one active voucher package. The application looks the ticket up again immediately before issuing, and the existing SQL transaction prevents duplicate voucher assignment.

In Development, configure Webtickets under the user-secrets store of the application you are running. For the Voucher System, username/password credentials use HTTP Basic authentication:

```powershell
dotnet user-secrets set "WebTickets:BaseUrl" "https://www.webtickets.co.za/api/transaction/cableway/lookup" --project TicketVoucherSystemApp
dotnet user-secrets set "WebTickets:CountryCode" "ZA" --project TicketVoucherSystemApp
dotnet user-secrets set "WebTickets:Username" "YOUR_USERNAME" --project TicketVoucherSystemApp
dotnet user-secrets set "WebTickets:Password" "YOUR_PASSWORD" --project TicketVoucherSystemApp
```

`WebTickets:BaseUrl` accepts either the site root or the complete lookup URL. A full `WebTickets:Endpoint` remains available as an override.

User secrets are not loaded when the deployed app runs in Production. Configure these keys in the IIS hosting environment, using double underscores for nested environment-variable names:

```text
WebTickets__BaseUrl=https://www.webtickets.co.za/api/transaction/cableway/lookup
WebTickets__CountryCode=ZA
WebTickets__Username=YOUR_USERNAME
WebTickets__Password=YOUR_PASSWORD
```

Recycle the IIS application pool after changing its environment. For bearer or API-key authentication, set `WebTickets__BearerToken`, or both `WebTickets__ApiKeyHeaderName` and `WebTickets__ApiKey`, instead. Authentication values are never sent to the browser or written to application logs.
